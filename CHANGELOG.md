# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Added

- **Prebuilt binaries on every release.** Each GitHub release carries archives with `agentguard`, `agentguard-mcp-gateway` and `agentguard-llm-proxy` for Linux, macOS and Windows on amd64 and arm64, a `checksums.txt`, and signed build provenance (`gh attestation verify <file> --repo Caua-ferraz/AgentGuard`). Installing no longer needs a Go toolchain. `scripts/build-release.sh` (`make release-artifacts`) builds the same archives locally, and refuses a version that differs from the one in the sources.
- **One-line installers that also update.** `install.sh` (Linux, macOS) and `install.ps1` (Windows) are attached to each release, stamped with its version, so `…/releases/latest/download/install.sh` always installs the newest release. They check the archive against `checksums.txt` before installing anything, install all three binaries, write a starter policy only when none exists, and print `Updated X -> Y` when run over an older install. `AGENTGUARD_VERSION`, `AGENTGUARD_INSTALL_DIR` and `AGENTGUARD_DOWNLOAD_URL` pin a version, choose the folder, or point at a mirror. See [`docs/SETUP.md`](docs/SETUP.md#1-install).
- **Published container image.** `ghcr.io/caua-ferraz/agentguard` is pushed for every release, for linux/amd64 and linux/arm64, tagged with the version and `latest`. Only the newest release moves `latest`. The image holds all three binaries; the server is still the default entrypoint.
- **Assets for existing releases.** The `Release binaries, installers and image` workflow can be run by hand with a tag to build and attach the same assets to a release published before it existed.
- **Installer smoke test.** After every release's assets are uploaded, `.github/workflows/installer-smoke.yml` installs AgentGuard the documented ways (the one-liners on Linux x64 and arm64, Alpine, macOS on Apple silicon and Intel, and Windows PowerShell 5.1 and 7, plus the container image) and checks the version, all three binaries, the starter policy, a rerun that keeps the operator's policy, and that a tampered archive is refused. Pull requests that touch the installers run the same checks against their own scripts.
- **Uninstall.** `install.sh --uninstall` (`curl -fsSL …/install.sh | sh -s -- --uninstall`) and `AGENTGUARD_UNINSTALL=1` with `install.ps1` remove the three binaries — on Windows also the user PATH entry the installer added, and its now-empty default folders — and keep the policy folder, saying where it is; `--purge` / `AGENTGUARD_PURGE=1` deletes it too. Audit logs and the state database are left alone. Running it when nothing is installed says so and succeeds; on Windows it refuses, before removing anything, while AgentGuard is running. See [`docs/SETUP.md`](docs/SETUP.md#uninstall).
- **`agentguard setup`: set up, update and uninstall from a menu.** A menu — arrow keys and Enter, no flags — that sets AgentGuard up for your user: the starter policy, a data folder for the audit log and database, an API key only you can read, and a login service that starts the server (a systemd user service, a LaunchAgent, or a Task Scheduler task; no admin rights). Later runs show the server's state and open the dashboard (with the key on the clipboard), update in place (download, `checksums.txt` check, binary swap, service restart), start or restart the server, print the connection settings for the SDKs and a Claude Desktop block with no secret in it, open the policy, and — last, behind a choice that offers stopping the server first — uninstall, keeping or deleting the policy and data. It works offline except for the update, and needs a terminal: scripts keep using the installers. See [`docs/CLI.md`](docs/CLI.md#agentguard-setup).
- **Claude Code integration.** *Connect Claude Code* in `agentguard setup` adds a hook to Claude Code's user settings (`~/.claude/settings.json`, keeping everything else and a backup): before each shell command, file read or edit, web fetch or MCP tool call, Claude Code runs `agentguard hook claude-code`, which checks it on the running server as agent `claude-code` (transport `claude_code` in the audit log and dashboard). An allowed call carries on under Claude Code's own permissions; a denied one is blocked and Claude sees why; one that needs approval waits up to 5 minutes for an approval in the dashboard or with `agentguard approve`, and is audited as approved; with the server down, the call goes ahead with a warning. *Disconnect Claude Code* and uninstalling remove the hook. See [`docs/CLAUDE_CODE.md`](docs/CLAUDE_CODE.md).
- **Claude Code rules in the starter policy.** It ends with rules for agent `claude-code` (`configs/claude-code.yaml`, `override_mode: replace`): read and write anywhere except credentials and system folders, `.env` files and destructive commands (`sudo`, `rm -rf`, force-push, `git reset --hard`, `curl … | sh`) behind approval, any web host except cloud metadata endpoints. Other agents keep the sandbox rules. *Connect Claude Code* offers to add the block to an older policy, as text so comments stay, and leaves the file alone if the result wouldn't load or would change anything else.
- **The LLM API proxy knows Claude Code's tool names** (`Bash`, `PowerShell`, `Read`, `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, `Glob`, `Grep`, `WebFetch`). They were unmapped — names are matched case-sensitively — so Claude Code routed through the proxy was denied almost everything.
- **`agentguard server --api-key-file`.** Reads the key from a file, so it stays out of the command line, service definitions and the process list. The server refuses to start if the file is missing or empty.
- **The saved key is the last fallback for clients.** `approve`, `deny`, `status`, `audit`, the MCP gateway and the LLM proxy use the key `agentguard setup` saved when neither `--api-key` nor `AGENTGUARD_API_KEY` is set. The server never reads it by itself.
- **`agentguard server`.** The server command's documented name is now `server`. `serve` runs the same command and stays for the whole 1.x line. The docs, the Dockerfile's default command and the installers' "Next:" line use `server`.
- **`agentguard help`.** `agentguard help`, `-h` and `--help` print the command list, grouped by what you're doing, on stdout and exit 0; they printed it on stderr and exited 1. `agentguard help <command>` prints that command's help. The command list starts new users off (`agentguard server --dashboard`, then the dashboard URL), names the MCP gateway and LLM proxy, and links the docs for the installed version. Every command's help has examples and says what its exit codes mean; `check` groups its flags into describing the action, JSON input, and policy and output, and says that its `--url` is the action's target, not the server. `server -h` groups the 32 server flags by topic (network, security, policy, audit log, storage, multi-node, notifications, debugging). `tenant` warns that it must use the server's `--data-dir` or `--store-dsn`, and `tenant put` repeats it; `migrate` says the server already migrates at startup. The MCP gateway and LLM proxy print their help the same way: `--flag`, grouped, 80 columns.
- **The policy file is found automatically.** When `--policy` is not given, `server`, `validate` and `check` use `AGENTGUARD_POLICY`, then `configs/default.yaml` in the current folder (as before), then the starter policy the installer wrote (`~/.config/agentguard/default.yaml`, `/etc/agentguard/default.yaml`, or `%APPDATA%\agentguard\default.yaml` on Windows). After installing, `agentguard server --dashboard` starts from any folder. `validate` also takes the file as an argument (`agentguard validate policy.yaml`), and `check` no longer requires `--policy`. See [`docs/CLI.md`](docs/CLI.md#policy-file).
- **`AGENTGUARD_URL` for the CLI and the gate binaries.** `approve`, `deny`, `status` and `audit` read it when `--url` is not given, as the SDKs already did, and accept `--guard-url` as another name for `--url`. `agentguard-mcp-gateway` and `agentguard-llm-proxy` read it when `--guard-url` is not given. A flag always wins over the variable.

### Changed

- **The update notice names the command that updates.** It read `agentguard v1.2.0 is deprecated, version v1.3.0 available — <releases page>`; it now reads `AgentGuard v1.3.0 is available (you have v1.2.0). Update: <command> — what's new: <releases page>`, where the command matches how that copy was installed: the one-line installer for its OS, `go install …@latest`, or `docker pull` for the container image, which now sets `AGENTGUARD_DISTRIBUTION=container`. The server still never checks.
- **The installers say what they changed.** Besides `Updated X -> Y`, a rerun on the same version prints `Reinstalled … (it was already on this version)`, and installing an older release than the one present prints `Downgraded X -> Y` and a warning. The install still goes ahead — a pinned rollback is deliberate.
- **The Dockerfile cross-compiles.** The builder stage runs on the build host's platform and compiles for BuildKit's `TARGETOS`/`TARGETARCH`, so a multi-arch build needs no CPU emulation. A plain `docker build` still produces an image for the host, with the same entrypoint and default command.

- **Command-line mistakes say what to do.** An unknown command or flag suggests the nearest one (`agentguard --serve` → `Did you mean 'agentguard server'?`, `--polcy` → `did you mean --policy?`) instead of printing the whole usage. A missing or extra argument is named. These exit 2, like a bad flag always did; running `agentguard` with no command, and `approve`/`deny` without an ID, exited 1. `approve`, `deny`, `status` and `audit` report an unreachable server as `Cannot connect to AgentGuard at … (connection refused). Is 'agentguard server' running there?`, a 401 as a missing or rejected API key, and a `--url` without `http://` before sending anything. `approve` and `deny` print `Approved <id>` / `Denied <id>` instead of `Action approve: approved`.
- **The update notice says `agentguard setup`** for copies the installers put there, instead of the installer one-liner; the installers' closing line suggests it too.
- **The update check also skips help and mistyped commands**, so help prints without waiting on the network. `server` still never checks.
- **`--watch` says what it does.** Its help now says it only adds a log line per policy reload; the server reloads the policy either way. The server's startup log names the policy file it loaded.
- **The LLM proxy prints one warning for a missing `--api-key`**, not two.

### Fixed

- **Flags after a positional argument were ignored.** Go's flag parsing stopped at the first argument, so `agentguard approve ap_… --url https://guard.example` approved on `http://localhost:8080` instead. Flags can now come before or after arguments on every command; `--` still ends them.
- **`agentguard validate broken.yaml` printed VALID.** The file argument was ignored and `configs/default.yaml` was validated instead.
- **Stray arguments were ignored.** Every command now rejects an argument it doesn't take. `agentguard-llm-proxy version` started the proxy; it now answers `did you mean --version?`. On `agentguard-mcp-gateway`, an unquoted `--upstream fs:npx … /tmp` launched the server without `/tmp`; the gateway now refuses to start and says to quote the command.
- **`approve` and `deny` misreported an unknown ID or a missing API key.** The server answers those in plain text, which the CLI tried to decode as JSON and printed `Error decoding response: invalid character …`. It now prints `no pending approval <id>` and the API-key message.
- **Two help lines showed a command as a flag's value type.** `--tenant-policy-refresh-interval` and `migrate --checkpoint` quoted a command in backquotes, which Go's flag package takes as the value's name (`-checkpoint agentguard serve`).
- **The MCP gateway ignored `--reconnect-cap`.** It was parsed but never applied, so an upstream that kept exiting was always retried on the fixed 1s, 2s, 5s, 30s, 60s schedule. The schedule now stops at the flag's value.
- **`agentguard tenant <typo>` created an empty `agentguard.db`** in the current folder before reporting the unknown subcommand.
- **The PATH hint names the file your shell reads.** When the install folder is not on `PATH`, `install.sh` suggested adding it to `~/.profile`, which zsh — macOS's default shell — never reads, so `agentguard` vanished in the next terminal. It now names `~/.zshrc` for zsh, `~/.bash_profile` for bash on macOS, `~/.bashrc` for bash on Linux, `fish_add_path` for fish, and `~/.profile` otherwise. The installers attached to v1.2.0 still print `~/.profile`.

## [1.2.0] — 2026-09-24

> **A security release from a full local test of 1.1.1.** Instead of relying on CI alone, the test ran every surface in a sandbox: the CLI, the server, approvals, audit, persistence, multi-tenant and multi-node PostgreSQL deployments, the MCP gateway, the LLM proxy, both SDKs and the dashboard. It found one high-severity bypass. A shell allow rule's glob matched the whole command line, so `allow: "ls *"` also allowed `ls /tmp; rm -rf /`, and chained commands got past the default policy's `sudo` and `rm -rf` approval rules. It also found nine medium-severity problems. Among them: a second rule block for a scope was silently ignored; secrets were stored verbatim in the audit trail; and `pip install agentguardproxy[all]` installed a CrewAI version on which the adapter gated nothing. Rerunning the test against the fixes found one more bypass, in the MCP gateway's network check.
>
> **No field, route, flag or schema version was removed or changed.** The new flags, the `order` query parameter and the Go additions are all additive. Three of the security fixes change what an existing policy decides, and one kind of policy no longer loads: two blocks for one scope that set different rate or cost limits. See *Compatibility* and [`docs/MIGRATION.md`](docs/MIGRATION.md#v11x--v120).

### Security

- **Compound shell commands are checked one command at a time.** A shell rule's pattern was a glob over the whole command, and one `*` matched every character, so `allow: "ls *"` also allowed `ls /tmp; rm -rf /`, `ls $(rm -rf ~)`, `git clone x && sudo rm -rf /` and `echo x > /etc/passwd`. A line break worked too, because request normalization stripped it before matching. A command that contains shell syntax is now split by a quote-aware tokenizer (`pkg/policy/shell_segments.go`) into the simple commands a POSIX shell would run, including those inside `$( )`, backticks, `<( )` and subshells. Whole-command deny and approval rules run first; then each command goes through deny, approval and allow on its own, and the most severe verdict wins. Redirection targets are checked as filesystem writes or reads. Heredocs, arithmetic expansion, unbalanced quotes and nesting deeper than 8 levels are denied as `deny:shell:unparseable_command`. An allow pattern that contains shell syntax itself (`cat * | head *`) matches command by command. A command without shell syntax takes the same path as before, at 1.1.1's speed and allocations; a compound check costs about 1.1 µs. A fuzz target ran about 15 million inputs without a failure.
- **Rule blocks that share a scope are merged.** Evaluation stopped at the first block for a scope that decided, so `allow: "*"` followed by a separate `deny: "rm *"` block allowed `rm -rf /`, and `validate` reported the policy as VALID. Blocks with the same scope, in `rules:` or in one agent's `override:`, are merged at load in file order, so deny, then approval, then allow holds across them. Each merge is a load warning. A `rate_limit` or cost `limits` that differs between merged blocks is a load error.
- **Secrets are masked in the audit trail by default.** Keys, tokens and passwords in an agent's command were stored verbatim in the audit log (file and store) and shown by `GET /v1/audit`, the SSE stream, the dashboard and `/api/pending`; only notifications were redacted. `serve --audit-redact` (default `true`) masks them on all of those surfaces, using the notification redactor plus the policy's `notifications.redaction.extra_patterns`. The regex work runs in the audit workers, off the `/v1/check` request path. `/api/pending` returns redacted copies, so the queued request that approval replay compares stays intact. The MCP gateway's and LLM proxy's `--fail-audit-log` entries use the built-in patterns. `--audit-redact=false` stores requests verbatim and logs a startup warning.
- **The default redaction patterns cover the secrets agents handle.** In addition to Bearer tokens, AWS keys, `ghp_` tokens, Slack tokens and `secret=`/`token=`/`password=`/`api_key=` pairs, they now match `sk-…` LLM API keys, Google `AIza…` keys, the other GitHub token types (`gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), JWTs, PEM private keys, and `Authorization` / `x-api-key` header values. Notifications and the Python MCP adapter's error text use the same list; a test keeps the Python copy identical to the Go one.
- **The default policy denies the filesystem MCP server's other write tools.** `configs/default.yaml` denied `*:write_file` with "Writes via MCP are blocked by default policy", but `edit_file`, `move_file` and `create_directory` matched the `fs:*` allow; the test edited a file and created a directory through the gateway. Those three tools are now denied with the same message. They're listed by exact name, so `github:create_issue` stays on the approval path.
- **The MCP gateway checks a tool's URL host, not a `domain` argument next to it.** For a tool mapped to `network` or `browser`, the gateway took the domain from a `domain`, `host` or `hostname` argument, and used the URL's host only when those were empty. The model writes the arguments, so `{"url": "https://evil.example/x", "domain": "api.github.com"}` passed an allow-list for `api.github.com` while the tool fetched `evil.example`. Whenever there's a `url` argument, the gateway now uses its host, as the LLM API Proxy already did; a relative or malformed URL gives no domain and is denied. The Python MCP adapter had the same override and is fixed too. 1.1.x behaves the same way; this was found while verifying 1.2.0.
- **The CrewAI adapter refuses CrewAI below 1.0.** `pip install agentguardproxy[all]` resolved CrewAI 0.193, where wrapping a tool raised `TypeError`. With that fixed, a crew still ran its tools without a single `/v1/check` call, because CrewAI 0.19x dispatches agent tool calls through a path the adapter doesn't wrap. The adapter now raises `ImportError` below 1.0 rather than return tools that look gated but aren't, and the `crewai` extra is `>=1.0,<2.0`.

### Fixed

- **`network` and `browser` checks that carry only a `url` are matched against its host.** `POLICY_REFERENCE.md` says a domain rule matches the URL's host when `domain` is empty, but the engine read only `domain`, so every such check was denied by default, even for an allow-listed host. The host is taken from absolute URLs, lower-cased, without port or userinfo: `https://api.github.com@evil.com/` is checked as `evil.com`. An explicit `domain` still wins.
- **Lifetime decision counters survive archive pruning.** The replay checkpoint was written once, at startup. After more than `--audit-max-backups` rotations, the archive it pointed to was pruned, and the next startup could only recount the files still on disk: in the test, 4,000 decisions became 2,268. The file audit logger now rewrites the checkpoint after each rotation (before pruning) and on shutdown. The same scenario reads 2,666 allowed and 1,334 denied before and after the restart.
- **`agentguard audit --limit N` shows the newest N entries.** `GET /v1/audit` returned the oldest matches for `limit=N`, so on a busy server the CLI and the dashboard's history showed the first entries in the log, not recent activity. The CLI (`--order`, default `desc`) and the dashboard now ask for the newest first; see *Added*.
- **`pip install agentguardproxy[all]` resolves to supported versions.** It now resolves to CrewAI 1.15, browser-use 0.11, LangChain 1.4, MCP 1.28 and pydantic 2.12, with a clean `pip check`. The `mcp` extra allows MCP 2.x (`<3.0`); the MCP adapter and gateway suites pass on 2.1.1 and 2.2.0. `CrewStructuredTool` now receives only the keywords its constructor accepts.

### Added

- **`serve --bind <host>`** sets the listen address. A server with `--api-key` listened on every interface with no way to narrow it, so a reverse proxy on the same host could be bypassed over the plaintext port. Without `--api-key`, only a loopback address is accepted; anything else exits with status 2 before listening. Empty (the default) keeps the existing behaviour.
- **`agentguard validate --strict`** exits 1 when the policy loads with warnings. Scope names one or two edits from a built-in scope (`shel`, `filesytem`, `Shell`) are a new load warning ("did you mean shell?"); custom scopes still work. `make validate`, `scripts/test-all.sh` and CI use `--strict`.
- **`GET /v1/audit?order=asc|desc`** and its tenant mirror. The default stays `asc`; any other value returns 400. `agentguard audit --order` defaults to `desc`.
- **`agentguard --version`** and `-version`, like the other two binaries.
- **Python: `agentguard.__version__`.**
- **Go:** `policy.LoadFromFileWithWarnings`; `proxy.IsLoopbackHost` and `proxy.Config.Redactor` / `BindHost`; `audit.WithTransform`, `audit.EntryTransform`, `audit.Checkpointer`, `(*audit.FileLogger).EnableCheckpoints`, `audit.QueryFilter.Desc` and `audit.BufferedAsyncOpts.Transform`; `(*notify.Redactor).RedactRequest` and `RedactString`.
- **CI runs the `test_at_*` suites.** They exercise a real agent loop, the real LLM proxy, and the MCP gateway adapter against a real stdio server. They were marked `integration`, so `python-test` deselected them, and `integration-tests` ran only `test_real_<framework>.py`. Each framework leg now runs its `test_at_real_*` file, the LangChain leg builds `agentguard-llm-proxy` and runs its end-to-end suite, and a new required `mcp` leg runs the gateway suite. A new advisory `python-extras-all` job installs `.[all,dev]` into a fresh environment, runs `pip check` and the whole Python suite.

### Changed

- **`configs/default.yaml`:** `find … -exec`, `-ok` and `-delete` require approval, and the MCP write tools above are denied. The comment that said writes could be re-allowed with a narrower allow rule now says to remove or narrow the deny line, since deny is checked first.
- **The real-server end-to-end test fixture passes `--data-dir`**, so a run no longer leaves an `agentguard.db` in `plugins/python` that failed the session-cost tests on the next run.

### Compatibility

- **Policy decisions can change.** A shell chain or pipeline is allowed only when every command in it is (`cat README.md | head -5` was allowed by the default policy and is now denied, because no rule allows `head`). Redirections are checked against filesystem rules. Rules in a second block for a scope now apply. `url`-only network and browser checks that were denied can be allowed. `validate --strict` and the replay recipe in `MIGRATION.md` show what changes for your policy.
- **A policy with two blocks for one scope that set different `rate_limit`s or cost `limits` fails to load.** `serve` exits at startup; a hot reload keeps the previous policy.
- **Audit content is masked by default.** `--audit-redact=false` restores verbatim content. Entries already on disk are not rewritten.
- **`agentguard audit` lists newest first.** `--order asc` restores the old order; the HTTP default is unchanged.
- **The shipped `configs/default.yaml` changed** (see *Changed*). A copy you made earlier is unaffected.
- **The CrewAI adapter needs CrewAI 1.0 or newer.**
- **MCP gateway and Python MCP adapter:** a `network` or `browser` tool call with both a `url` and a `domain`/`host`/`hostname` argument is checked against the URL's host.
- Downgrade to 1.1.x is safe: nothing on disk changed format. It brings back the bypasses above.

## [1.1.1] — 2026-09-23

> **A patch release from an audit of names, ownership and docs against the code.** It checked every install command, contact address, example config and documented behaviour against what exists. The worst findings weren't in the code. The docs told TypeScript users to install `@agentguard/sdk`, an npm package owned by an unrelated project. The security contact address didn't exist, so vulnerability reports sent to it were never received. Three release notes told Docker users to pull an image that was never published. And the example MCP configs launched a fetch server package that has never existed. One finding was in the code: `agentguard-llm-proxy --listen :PORT` started on every interface with no inbound auth.
>

## [1.1.0] — 2026-09-13

> **A correctness-and-honesty release, from a review of the packages no prior audit had opened** (`pkg/metrics`, `pkg/depaudit`, `pkg/migrate`, `cmd/agentguard`, and both plugin SDKs). Six findings, all fixed. Two of them are behaviours the docs described that the code never implemented: `agentguard migrate --reset-checkpoint` deleted a file that did not exist and reported success, and the SDKs could not replay an approval at all, so the one-shot / validity / cost-reservation semantics documented for `/v1/check` never applied to SDK callers. A third is a defect invisible from the outside: the default audit pipeline never exposed its file path, so **no production deployment had ever written a replay checkpoint** — every boot re-scanned the entire live audit log, and the decision counters restarted from zero. Landing alongside them are five LLM-proxy gating fixes (B6, B7, B17, B18, B21), each one a stream or response the firewall could not evaluate and forwarded, dropped, or wrongly refused anyway. Landing alongside *those* are five more that only a running cluster could produce: a migration race that killed replicas at boot, a rotation that destroyed archives, a flush deadlock between nodes, streaming refusals that reached the client but never the audit trail, and a checkpoint path no deployment had ever written to. Eighteen fixes in all.
>
> **The `/v1/check` hot path is untouched** and its benchmarks sit at their recorded baselines. The streaming accumulators, which are also enumerated hot path, *are* touched: their per-event cost was measured against the pre-change tree rather than assumed — identical allocations on every path, timing differences inside run-to-run noise. Additive-only vs 1.0.0 with one deliberate exception, stated under *Compatibility*: an OpenAI stream returning tool calls on more than one `choice` is now refused rather than silently merged.

### Fixed

- **Undecodable non-streaming responses that carry a tool call now fail closed (audit B6).** The gated non-streaming path decoded the upstream body into the typed response struct and, on failure, forwarded it verbatim — on the sound principle that AgentGuard never rewrites an already-corrupt wire. The flaw was treating "Go cannot decode this" as "the client cannot use this". `encoding/json` aborts on a **type-mismatched** field the struct declares, such as `"created":"1730000000"` where the spec says integer, while a Python or TypeScript SDK ignores the odd field and executes the `tool_calls` sitting beside it. The result was a tool call the firewall never evaluated. No attacker is required: `--upstream-openai` is a supported flag, so pointing the proxy at an OpenAI-compatible shim (vLLM, Ollama, LiteLLM, a cloud gateway) is a normal deployment, and those layers routinely stringify a numeric field. Before falling back to passthrough the proxy now runs a probe that constrains only the path to `tool_calls` / `tool_use`, so nothing outside it can impose a type constraint; if a tool call is present the response is refused under the stable rule `deny:llm_api_proxy:undecodable_tool_call` and recorded in the central audit trail with the DENY the client received, via the same `/v1/audit` ingest the malformed-tool-call refusal uses. A body with no tool call keeps its verbatim passthrough untouched — this narrows the rule rather than reversing it, which is why the existing passthrough test still passes unmodified. The refusal is deliberately **not** subject to `--fail-mode allow`, matching the duplicate-JSON-key deny: `--fail-mode` governs an unreachable guard, whereas here the guard is healthy and simply cannot see what the client will execute. Note a JSON `null` or an unknown extra field is not a type error, so neither diverts a response down this path. Streaming is unaffected; it is gated by the accumulator, which has its own fail-closed defences. Verified end to end against a containerised shim upstream: the refusal reaches the client and the audit entry lands tagged `transport: llm_api_proxy`.

- **Two rotations inside the same second no longer destroy the first archive.** Archive names carry a one-second timestamp (`20060102T150405Z`) and `rotateLocked` renames the live file onto that name, so a burst that rotated twice within a second computed the same target twice and `os.Rename` replaced the earlier archive — real audit data gone, with no error anywhere, and the `_meta.rotated_from` chain that startup replay walks broken at that link. The rotator now advances the timestamp to the next free second instead of overwriting. Advancing rather than adding a `-N` suffix is deliberate: `pruneArchivesWithAge` only recognises a name whose suffix is exactly the length of the timestamp format, so a suffixed archive would be invisible to both count- and age-based pruning and would never be deleted. The cost is that a name can read up to a minute later than the instant it rotated; the entries inside carry their own timestamps. If every slot in that window is taken the rotation fails and the live file keeps growing, which an operator can recover from — unlike a destroyed archive. The test workaround that had been sleeping 1.1s between rotations to dodge this is gone, taking the audit package's suite from 16.5s to 7.9s.
- **Structural streaming refusals now reach the audit trail.** A stream refused because it could not be gated — interleaved `tool_use`, orphaned tool input, tool calls across several choices — or because it blew `--max-buffer-bytes` produced a client-visible refusal and **no audit entry at all**. The gate never runs on those paths, so the `/v1/check` call that normally writes the entry was never made, and the only signal was a counter in the proxy's process-local registry, which has no scrape endpoint: the operator saw nothing. All six such branches (three per provider) now record the refusal with its rule, tenant, agent and provider, plus whatever tool identity the parser observed first. Confirmed against the container cluster before the fix: the orphaned-input and multi-choice scenarios returned `null` from `/v1/audit` while the neighbouring gated scenarios produced entries.
- **A stream that ends mid-tool-call is now gated instead of dropped (audit B17).** When upstream hit EOF — a dropped connection, or a provider that ends the stream without a terminal `finish_reason` — while a tool call was still buffered, the loop simply returned and the buffered events went on the floor. The client got an empty `200`, the gate never ran, and nothing was audited: the firewall went dark at exactly the moment a truncated tool call was in flight. The accumulator's own comment said the orchestrator should "flush whatever's buffered as-is" at that point, which would have been **worse** — those bytes are the ungated tool call, and flushing them is the bypass this machinery exists to prevent. The cycle now runs the **completion** path instead: arguments that parse are gated normally and, on ALLOW, replayed byte-identical; arguments truncated by the cut do not parse and land on the existing `deny:llm_api_proxy:malformed_tool_call` refusal, denied and audited. Both providers are fixed symmetrically. `[DONE]` is additionally treated as the end of the stream in its own right rather than deferring to the transport EOF, so a gateway that holds the connection open after it no longer delays the verdict. A completion latch keeps the two new closers from re-gating a cycle `finish_reason` already closed.
- **Tool calls spread across several OpenAI choices are refused rather than merged (audit B18).** Accumulator state is keyed by `tool_calls[i].index`, which is unique only **within** one choice. With `n > 1` both choices number their calls from `0`, so two different calls' argument fragments concatenated into a single state: the gate evaluated a splice no client would ever execute, while the two real calls reached the client unexamined. A second defect compounded it — any choice's `finish_reason` closed the cycle, so a sibling choice finishing first gated a truncated argument string and refused a healthy stream. Tool-call deltas now claim the cycle for the choice that carried them: a second choice carrying tool calls fails the stream closed under the new rule `deny:llm_api_proxy:multi_choice_tool_calls`, and only the owning choice's `finish_reason` closes the cycle. The honest trade is stated in `docs/LLM_API_PROXY.md`: this costs `n > 1` **with tool calls**, which never worked correctly anyway. `n = 1` — what every mainstream agent framework sends — is byte-identical to before.
- **Anthropic tool input arriving outside any `tool_use` block is refused (audit B7).** An `input_json_delta` is only meaningful inside an open `tool_use` content block; the block index is what binds the fragments to a call. One arriving while idle was forwarded verbatim by the parser's catch-all pass-through, so tool-call **argument bytes** belonging to a call the firewall never saw start reached the client — with no cycle in existence that could ever have gated them, and no audit entry. They are now refused under the new rule `deny:llm_api_proxy:orphaned_tool_input`, the same fail-closed posture the neighbouring interleaved-`tool_use` defence already took. Idle **text** deltas — the overwhelming majority of events on that branch — still pass through untouched; only `input_json_delta` diverts.
- **`{ }` in an Anthropic `content_block_start` no longer refuses a legitimate stream (audit B21).** The H2 defence seeds tool arguments from a non-empty start-block `input` and then fails closed if `input_json_delta` fragments stream for the same block, because the two argument sources conflict. "Non-empty" was decided by `bytes.Equal` against the literal `{}`, so `{ }` or `{\n}` — the same empty object to every JSON reader — was mistaken for real arguments, and the very next delta (the **conformant** way Anthropic streams them) tripped the conflict refusal. Emptiness is now a structural question, answered by an allocation-free byte scan rather than a `json.Unmarshal` that would allocate a map on the streaming hot path. A malformed seed still counts as real arguments, which keeps the failure direction closed.
- **Concurrent nodes no longer deadlock while flushing counters to Postgres.** The write-behind syncer builds each batch by ranging over a Go map, whose iteration order is randomized per call, and Postgres holds a row lock on every upserted row until the transaction commits. Two nodes writing the same keys in opposite orders is an AB/BA inversion, and the server breaks it the only way it can — by killing one transaction (`SQLSTATE 40P01`), which discards that node's whole tick of writes. Measured in a three-node container cluster under load: **393 deadlocks, 386 of them on `approvals`**, which carries by far the largest batch. No counter was permanently lost — memory stays authoritative and the flush is snapshot-based, so the next tick rewrote the same state — but the cold tier went stale for as long as the flushes kept failing, and cross-node approval visibility went with it. The three batches whose conflict key is shared between nodes (`approvals`, `rate_buckets`, `session_costs`) are now sorted by that key before the transaction, giving every writer one global lock order and making the inversion structurally impossible rather than merely rarer. The consumption tables carry `node_id` in their key, so each node writes a disjoint row set and has nothing to invert against. A deadlock abort rolls its transaction back whole, so the cases sorting cannot remove — a purge `DELETE` scanning rows against a concurrent upsert — are now retried up to three times with backoff rather than dropping the batch. SQLite is unaffected: it admits one writer at a time database-wide. After the fix the same soak, at ~5.1M requests across three nodes, produced **zero** deadlocks.
- **Replicas no longer lose nodes to a schema-migration race.** `PostgresStore.Migrate` ran every DDL statement in its own transaction with no mutual exclusion, so replicas starting together raced each other and the losing node's constructor failed — the process logged `Failed to open store` and exited 1. Two distinct failures, both reproduced: against an **empty** database `CREATE TABLE IF NOT EXISTS` is not atomic against a concurrent creator, so nodes collide on the `pg_type` unique index (`SQLSTATE 23505`); against an **existing** schema the `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements still take ACCESS EXCLUSIVE locks even with nothing to add, so concurrent migrations deadlock (`SQLSTATE 40P01`). Measured in a three-replica container cluster: **5 of 6 cold starts lost at least one node** (once, two of three), while a single node never failed — which is what identified it as a race rather than a schema fault. The existing migration test only re-migrated *sequentially*, so it could not contend and never saw it. `Migrate` now takes a transaction-scoped advisory lock (`pg_advisory_xact_lock`) as its first statement, which serialises the whole migration cluster-wide and releases on commit or rollback, so a crashed migrator cannot wedge the cluster. After the fix: 6 of 6 cold starts and 5 of 5 simultaneous three-node restarts came up clean. SQLite is unaffected — it serialises writers at the file level and is the single-node backend by design.
- **The SDKs can now replay an approval — the one-shot, validity and cost semantics finally reach SDK callers.** `@guarded(wait_for_approval=True)` (Python) and `guarded(..., { waitForApproval: true })` (TypeScript) ran the wrapped function directly off the resolution they read from `GET /v1/status/{id}`. That read is **passive**: it spends nothing. The call that consumes the one-shot ALLOW, enforces `--approval-validity`, reserves cost for cost-scoped actions, and writes the `allow:approved` audit entry is a `/v1/check` **replay carrying `approval_id`** — and neither SDK had any way to send that field. So a `cost`-scoped action approved through the SDK executed with **no cost reserved** (the original check returned `REQUIRE_APPROVAL` before `checkCost` ran), one human click could authorise repeated executions, and the audit trail showed a resolution with no execution behind it. Both wrappers now replay after an ALLOW resolution and run the function **only if the replay allows**. A refused replay (consumed or expired) re-enters the approval flow server-side under a new id and is surfaced as `AgentGuardApprovalRequired` / `AgentGuardApprovalRequiredError` carrying that **new** id — the wrappers never wait a second time, so a refused replay cannot loop. `docs/APPROVAL_WORKFLOW.md` §5, which told operators to "re-run `check()` with the same parameters" (which would simply produce a fresh `REQUIRE_APPROVAL`), is rewritten with the correct sequence for both languages.
- **`agentguard migrate` addressed a checkpoint file that does not exist.** The subcommand computed `<audit-dir>/.replay-checkpoint` while `agentguard serve` reads and writes `<audit-log>.replay-checkpoint`. Two consequences, both silent: `--reset-checkpoint` printed `checkpoint removed` while deleting nothing, so the documented recovery procedure was a no-op; and a CLI-run migration rewrote the audit file **without** invalidating the server's real checkpoint, leaving a byte offset pointing into a file whose contents had shifted (the staleness guard does not catch this, because the rewritten file is *larger* than before). Every reader and writer — the startup seeder, the subcommand, and the v0.4.0 to v0.4.1 migration — now derives the path from one new function, `audit.CheckpointPath`. `--reset-checkpoint` reports honestly, printing `no checkpoint found at <path>` when there is nothing to delete. `runMigrate` had **no tests at all**, which is how this shipped; it is now a thin wrapper over a testable `executeMigrate`.
- **The v0.4.0 to v0.4.1 migration is now a no-op on an already-migrated file.** The framework's `--id` operator override runs `Migrate()` even when `Detect()` returned false. On a file that already carried a schema header this prepended a **second** `_meta` line, shifting every byte offset the replay checkpoint depends on, writing a backup of the already-migrated bytes, and deleting a still-valid checkpoint. It now detects the existing header, reports it in the result notes, and touches nothing.
- **Decision counters survive restarts, and the replay checkpoint works in production at all.** Two defects compounded here. First, the shipped audit pipeline wraps the `FileLogger` in a `BufferedAsyncLogger` (the `--audit-buffered` default), which did not implement the `Path() string` the startup seeder type-asserts for — so the checkpoint branch was **dead in every default deployment** and each boot re-scanned the whole live audit file, exactly the cost the checkpoint exists to avoid. Second, even where it did engage (`--audit-buffered=false`), the seeder replayed only the entries after the checkpoint into process-local counters, so after a restart `agentguard_checks_total`, `agentguard_allowed_total`, `agentguard_denied_total`, `agentguard_approval_required_total` and `/api/stats` reported only what had been written since the previous boot — while `docs/OPERATIONS.md` claimed they "survive restarts with accurate counters". The checkpoint now carries the lifetime tally (`counts`) and the live file's identity (`file_id`); boot seeds the counters from the tally and replays only what was written since. Verified end to end against the real binary across two restarts.
- **Startup replay follows the rotation chain.** A checkpoint written before a rotation used to be compared against the new live file by size alone. The seeder now recognises that the live file changed identity and walks `_meta.rotated_from` back through the archives — gzip or plain, decompressing transparently and treating the stored offset as an offset into the *uncompressed* stream — replaying the checkpointed segment from that offset and every newer segment from the start, oldest first. If the checkpointed segment has since been pruned, everything still reachable is replayed and the carried tally is preserved. The walk is bounded against a malformed or self-referential chain.
- **Corrupt lines skipped during startup replay now increment `agentguard_audit_corrupt_lines_total`.** `Query()` had always counted them; the replay path silently skipped them, so a gradually corrupting audit file degraded the boot-time seed with no signal at all. This also applies to the pre-existing exported `audit.ReplayFrom`, which shares the new scanner.
- **`agentguard serve` no longer calls out to the GitHub Releases API.** The enforcement server performed the startup update check like every other subcommand, meaning a long-running security component opened an outbound HTTPS connection the operator never configured, carrying a version-bearing `User-Agent`, and spent up to 800 ms of startup budget on it. Interactive subcommands keep the notice. Dev builds now skip it too: the check is bypassed when `commit=dev` — what a plain `go build` without the Makefile's `-ldflags` produces — which is what `docs/CLI.md` had always claimed.
- **TypeScript SDK: every request is bounded by `timeout`, and the bound covers the body.** `approve()`, `deny()` and each `waitForApproval()` poll had **no timeout whatsoever**, so an unresponsive server hung the calling agent indefinitely. `check()` armed an `AbortController` but cleared it the moment the response headers arrived, leaving a server that answers promptly and then stalls mid-body able to hang the agent forever. All four now run through one `withTimeout` helper that clears the timer only after the body has been consumed.
- **Python SDK: a malformed status body no longer aborts an approval wait.** `wait_for_approval` parsed the poll response outside its exception handling, so a middlebox returning an HTML error page with a 200 raised `JSONDecodeError` out of the loop and into the agent instead of being retried like every other transient poll failure. ## [1.0.0] — 2026-07-21

> **The validated 1.0 — multi-node, and the additive-only guarantee goes hard.** This is the release the v0.9 surface-stabilization was the step before. Two things define it. First, AgentGuard now runs as **more than one replica** against a shared **PostgreSQL** backend, with approval / rate-limit / cost state converging across nodes through a background reconcile loop — **without touching the `/v1/check` hot path** (no synchronous DB call was added; the <3 ms p99 budget is preserved and gated in CI). Second, the pre-1.0 validation window is over: from 1.0 the **additive-only** rule in [`docs/COMPATIBILITY.md`](docs/COMPATIBILITY.md) is a hard guarantee for the 1.x line, not an intent. A single-node deployment upgrades as a binary/SDK swap — multi-node is entirely opt-in behind a Postgres `--store-dsn`. This release also folds in the security, validation-hardening, and doc-honesty work done on the road to the 1.0 mark. Operators upgrading should read [`MIGRATION.md`](docs/MIGRATION.md) § v0.9.0 → v1.0.0 for the two behavior changes that matter (write-once / one-shot approvals).

### Added

- **PostgreSQL multi-node backend — shared state across replicas.** A Postgres `--store-dsn` (`postgres://…` / `postgresql://…`) selects a new `store.PostgresStore` (pgx v5, `database/sql` stdlib driver, pure-Go, mirroring `SQLiteStore`) behind the existing frozen `store.Store` interface. Approvals, rate-limit consumption, and cost accumulators are the shared durable tier; each node keeps its in-memory state authoritative and **converges in the background** via per-node-rows-summed consumption tables (`rate_consumption`, `cost_consumption`) and interval approval re-hydrate + merge. The zero-config single-node SQLite default is unchanged — the reconcile ticker never starts on SQLite. New exported surface for embedders: `store.NewPostgresStore`, the reconcile delta types (`ratelimit.BucketDelta`, `policy.CostDelta`, `store.RateConsumption`/`CostConsumption`), and the `ApprovalReplayRefusedTotal` / `IncApprovalReplayRefused` metric accessors. Semantics: [`docs/COMPATIBILITY.md`](docs/COMPATIBILITY.md#topology); operator sizing: [`docs/OPERATIONS.md`](docs/OPERATIONS.md#multi-instance-deployments). *(Corrected in v1.1.1: this linked an internal design doc that was never published.)*
- **`--node-id` serve flag** (default: OS hostname) — stable identifier for this node in multi-node reconciliation. Each replica MUST have a distinct value; an empty value disables reconciliation. Additive; single-node deployments never need it.
- **`--reconcile-interval` serve flag** (default `2s`) — cadence of the background rate-limit/cost/approval reconciliation loop. **Takes effect only with a Postgres `--store-dsn`**; on the SQLite backend it is forced to `0` and the loop never starts. `0` disables reconciliation.
- **`--approval-validity` serve flag** (default `5m`) — how long a resolved ALLOW is honored by the `/v1/check` approval-id retry, measured from resolution. Past the window the retry re-enters the approval flow under a new id; `0` restores the unbounded pre-v1.0 window. The default matches the SDKs' `wait_for_approval` poll window.
- **`POST /v1/audit` (+ `/v1/t/{tenant}/audit`) — auth-gated, DENY-only central audit-ingest endpoint.** Backs the F1 audit-verdict fidelity fix (see *Fixed*): when a proxy forces a fail-closed refusal for a malformed streaming tool call, it now records the **forced `malformed_tool_call` DENY** centrally via `handleAuditRecord` (single-source-of-truth preserved — the proxy still writes no local audit) instead of letting the policy verdict stand in the audit trail. Additive `policy.AuditRecord` type + `Server.RecordForcedAudit` → `gate.RecordForcedAudit` → `gateclient.Caller.RecordForcedAudit` wiring; a nil hook falls back to the prior audit-via-`PolicyCheck` path. On a `POST /v1/audit` record failure (canonical case: a keyed central server but an unkeyed proxy → 401), the proxy best-effort falls back to the `/v1/check` audit path so a forced refusal is never left un-audited — **fidelity** degrades to the engine verdict but **coverage does not**; give the proxy `--api-key` when the central server is keyed for full fidelity.

### Changed

- **Approval lifecycle hardening, enforced cluster-wide.** Resolutions are now **write-once**: re-approving an approved id (or re-denying a denied one) stays an idempotent no-op, but a *conflicting* re-resolution returns `409 Conflict` with a structured body (`policy.ApprovalConflictError`) instead of silently flipping the decision — the last-write-wins hole is closed. A resolved ALLOW is **one-shot and time-boxed**: the first `/v1/check` retry carrying the `approval_id` consumes it (`consumed_at`), later replays re-enter the approval flow, and honoring is bounded by `--approval-validity`. Across nodes these properties are preserved by a **monotonic merge**: `ApprovalQueue.ApplyRemote` merges remote resolutions DENY-wins and never clobbers unflushed local pendings, and `UpsertApprovals` on **both** store backends is a monotonic upsert — never un-resolves, never flips DENY→non-DENY, never clears `consumed_at`. So one human click is honored **once per cluster**, and a Postgres restart never resurrects a spent ALLOW.
- **Distributed rate limiting is bounded-overshoot by design, not global-strict.** Because reconciliation is background-only (to hold the no-sync-DB-on-`/v1/check` invariant), a cluster's aggregate admissions may exceed a single global budget by up to **≈ `reconcile-interval` × peak-rate × replicas** before convergence. This is a deliberate, documented trade — global-strict limiting would require a synchronous cross-node check on the hot path, which the latency budget forbids. Single-node behavior is exactly as before (the reconcile path is a proven no-op). See [`docs/COMPATIBILITY.md`](docs/COMPATIBILITY.md#topology).
- **Go toolchain pinned to `go1.25.12`** in `go.mod` (`toolchain` directive) — carries the stdlib fix for **GO-2026-5856** (crypto/tls Encrypted Client Hello privacy leak); go1.25.11 and earlier trip the CI govulncheck gate. See *Security*.
- **MCP Gateway protocol-coverage docs truthed-up (no behavior change to drop paths).** The gateway brokers `tools/*` only: `resources/*` and `prompts/*` capabilities are **masked** by `MergeCapabilities` (default dispatch is `MethodNotFound`), not "forwarded verbatim" as the old [`docs/MCP_GATEWAY.md`](docs/MCP_GATEWAY.md) § 3.3 / § 10 claimed. `notifications/cancelled` is documented as a latent no-op (host-space vs gateway-internal request-id spaces — § 8.4, which had overstated forward-to-upstream + cancel + audit). Server-initiated requests (`sampling/createMessage`, `roots/list`, `elicitation/create`) still drop, but a dropped frame carrying a `method` now logs at **Info** (was Debug) so operators see unsupported server→client requests. The README gained an "MCP brokers tools only" limitation bullet.
- **Contributor-facing `CLAUDE.md` now enumerates the latency hot path** — the exact packages/functions on the read-a-byte/forward path (`pkg/llmproxy` streaming/forward/parsers, `pkg/policy` `Engine.Check` & matchers, `pkg/proxy` `handleCheck`, `pkg/ratelimit` `Allow`, `pkg/internal/gateclient`), verified against code, so the "no sync DB / no blocking I/O / no per-request allocs on the hot path" rule is checkable rather than folklore. *(Corrected in v1.1.1: `CLAUDE.md` is not part of the published repository; the rule and the hot-path list are now in [`docs/CONTRIBUTING.md`](docs/CONTRIBUTING.md#latency-budget).)*
- **v1.0 documentation-accuracy pass.** README, COMPATIBILITY, MIGRATION, and the current-state docs are corrected to describe the shipped 1.0 behavior — multi-node Postgres, the bounded-overshoot semantics, approval write-once/one-shot lifecycle, and the F1–F3 fixes below — replacing v0.9-era "single-node is the supported topology / Postgres is post-v1" wording.

The SDK is on npm as `@lictorate/agentguard` from 1.1.1.)*

### Fixed

- **F1 — malformed streaming tool calls now fail closed (was: silent audit gap + stuck accumulator).** A completed tool call whose assembled arguments were not valid JSON returned `Completed:true` with a parse error and hit `if ferr != nil && !isEOF { continue }`, which skipped the gating switch entirely: no fail-closed refusal, no audit entry, and the accumulator's `activeToolUseIndex` was never reset, so the stream stayed broken for the rest of the connection (buffered bytes were dropped at EOF — not a client bypass, but an audit-visible stream went dark). Both providers now emit a fail-closed synthetic refusal (`denyMalformedOpenAI` / `denyMalformedAnthropic`), reset the accumulator, and continue. The **happy path is byte-identical** — only the malformed-completion branch changed; the `Allow` path stays 0-alloc. The follow-up audit-verdict fidelity fix (the forced DENY reaches the audit trail, not the policy verdict) is the `POST /v1/audit` ingest endpoint under *Added*.
- **F3 — `globMatch` documentation corrected to match code + non-fatal policy-lint warning.** A path pattern containing `/` but no `**` (e.g. `/workspace/*`) falls through to unanchored `wildcardMatch`, where `*` crosses `/` and matches `/workspace/a/b/secret.env` — contradicting `globMatch`'s own documented "stable contract." Matching **semantics are unchanged** (tightening them would break the frozen policy contract); instead the contract doc is corrected and `serve`/policy load now emits a non-breaking lint **warning** for patterns that match more broadly than they appear to. Operators relying on `/prefix/*` to bound a single directory should switch to an explicit `**`-anchored pattern.
- **MCP Gateway drop-path observability** — see *Changed*; unsupported server-initiated requests are no longer invisible at production log levels.
- **Python SDK filesystem-`action` inference now matches the Go transports** — the adapters (`agentguard/adapters/_common.py`) inferred the filesystem `action` by **substring** with a narrower verb set, so `edit_file`/`append_file`/`copy_*`/`move_*`/`unlink`/`rm*`/`list_*`/`stat`/`cat`/`find`/`glob` sent **no** `action` through LangChain/CrewAI/MCP while the Go transports (`gateclient.InferFilesystemAction`) sent one — and substring matching also mis-fired on names like `set_target` (contains "get"). Inference is now the same **prefix-matched** verb groups shared with `gateclient.InferFilesystemAction`, pinned by a parity test that mirrors the Go table. Operators whose policies key on filesystem `action` may see new (correct) matches through the Python adapters — the same class of change the v0.7 cross-transport skew fix documented.
- **Audit flush workers now isolate panics from the underlying logger.** A panic inside `underlying.Log` (a store-driver panic, a custom `MarshalJSON`, a nil-handle close race) escaped the `BufferedAsyncLogger` worker goroutine unrecovered and aborted the whole process, violating "a flush worker crash must never block or crash the proxy loop." The worker now recovers the panic and routes the entry to the existing overflow path (durable on disk, drop-accounted) instead of crashing — mirroring the panic isolation `pkg/notify`'s dispatcher already had.

### Security

- **F2 — domain matching is now case-insensitive (was a true fail-open deny bypass).** `normalizeRequest` never lowercased the request domain and `matchRule` → `globMatch` compared case-sensitively, so a deny rule for `evil.com` did **not** match the DNS-equivalent request `EVIL.com` — the deny was skipped and the request fell through to allow. Both the request domain (in `normalizeRequest`) and rule domains (at load) are now lowercased. No measurable hot-path cost (p99 ≈ 0.75 µs, no benchmark regression). Policies that accidentally relied on case-sensitive domain rules are now evaluated case-insensitively.
- **pgx bumped v5.9.1 → v5.9.2 — GHSA-j88v-2chj-qfwx (SQL injection).** v5.9.1 was vulnerable to SQL injection via dollar-quoted placeholder confusion; the advisory is reachable through the new Postgres backend. Both the reachability-based `govulncheck` job and the cross-ecosystem `dep-audit` gate fired correctly; verified clean live against OSV.dev post-bump.
- **crypto/tls Encrypted Client Hello privacy leak — GO-2026-5856.** Resolved by pinning the build toolchain to `go1.25.12` (see *Changed*).

### Compatibility

- **The v1.x additive-only guarantee formally begins with this release.** As declared in [`docs/COMPATIBILITY.md`](docs/COMPATIBILITY.md), no frozen field, route, flag, subcommand, scope, or schema version is removed, renamed, or repurposed across the 1.x line; only optional additive surface may be added, and consumers must tolerate unknown additive surface. A genuinely breaking change would be a major-version event behind a new identifier (`schema/v2`, audit `schema_version: 3`, a new route family), never a silent mutation. This release is **additive-only vs v0.9.0** — verified by diffing `go doc -short ./...` against the `v0.9.0` tag: **0 exported declarations removed**, and the only CLI-flag changes are the three additions above (`--approval-validity`, `--node-id`, `--reconcile-interval`).
- **One correction made under the pre-1.0 reserved right:** approval resolutions became write-once / one-shot (see *Changed*). This is the last-write-wins → write-once tightening documented in [`MIGRATION.md`](docs/MIGRATION.md#v090--v100); it is the reason the freeze is anchored at 1.0 rather than 0.9.
- **`/v1/check` request/response shapes, the audit format (`schema_version: 2`), and the policy schema (`version: "1"`) are byte-for-byte compatible with v0.9.**

### Migration

- **v0.9.0 → v1.0.0 is a binary/SDK swap for single-node deployments — no config or data changes required.** On first boot the SQLite/Postgres store applies an **additive, idempotent** schema migration (the `approvals` table gains `consumed_at` / `resolved_via` / `resolved_from`; the `rate_consumption` and `cost_consumption` tables are created); pre-v1.0 approvals load as unconsumed/unstamped and no rows are rewritten. `agentguard migrate` is not involved. Multi-node is opt-in: provision PostgreSQL, set `--store-dsn postgres://…` and a distinct `--node-id` per replica, and read the bounded-overshoot sizing note before setting `--reconcile-interval`. Rollback to v0.9.0 is supported (the extra columns/tables are ignored by the older binary), with two documented degradations. Full detail: [`MIGRATION.md`](docs/MIGRATION.md#v090--v100).

### Known limitations

- **A sustained multi-node soak against live PostgreSQL has not been run.** CI's `postgres-integration` job and the pg-gated tests cover multi-node **correctness** against a real Postgres 16, and the latency gates cover sustained single-process load, but a long-running, many-replica load test against a live shared Postgres is still outstanding and is recommended before production multi-node rollout.
- **Approval cross-node staleness is bounded by `--reconcile-interval` (default 2s).** The optional Postgres LISTEN/NOTIFY nudge to shrink this to sub-100 ms (`1-A-notify`) is not in 1.0; per-node deny remains fail-closed in the meantime.

> The consistency + durability release. Three workstreams land together (v0.6.0 was tagged but had no standalone release notes or CHANGELOG entry — its milestone is documented here):
>
> 1. **Persistent multi-tenant state** (the v0.6 milestone): `serve` is stateful by default — approvals, rate limits, and cost accumulators survive restarts via a zero-config SQLite store, and per-tenant policies are first-class (`agentguard tenant put`, isolated runtime state, tenant-scoped audit).

>
> Operator-facing summary: [`docs/releases/v0.7.0.md`](docs/releases/v0.7.0.md).

### Added
- **Local fallback audit on central-server outage** — both proxies' `--fail-mode fail-closed-with-audit` now appends each denial to `--fail-audit-log` (default `agentguard-fail-audit.jsonl`, canonical `audit.Entry` JSONL) while `/v1/check` is unreachable; the `_with_audit` suffix is no longer roadmap intent.
- **`agentguard check --watch <jsonl>`** — follow a JSONL file (tail -f) and verdict each appended request with one policy load for the whole stream (policy hot-reloads on edit); SIGINT returns the aggregate exit code.
- **Notify spool-to-disk (`--notify-spool`)** — notification events that overflow the dispatch queue spill to a JSONL spool and are redelivered by a recovery loop (including leftovers from a previous process) instead of being dropped. New counters `agentguard_notify_spooled_to_disk_total` / `agentguard_notify_despooled_total`.
- **MCP gateway forwards `notifications/tools/list_changed`** from upstreams to the host and now advertises `tools.listChanged: true`; hosts re-pull `tools/list` when an upstream's tool set changes.
- **Buffered-audit observability** — `agentguard_audit_buffered_dropped_to_overflow_total`, `agentguard_audit_buffered_drained_from_overflow_total`, and the `agentguard_audit_buffered_queue_depth` gauge.
- **Metrics-derived `/v1/health`** — corrupt audit lines and dropped notifications surface as warnings; an audit overflow backlog flips `status` to `"degraded"` (HTTP stays 200 so liveness probes don't flap).
- **LangChain stream re-gating** — `stream`/`astream` re-validate the policy decision every 10s (`STREAM_REGATE_SECONDS`) so a mid-stream revocation cuts the stream off instead of riding to completion.

- **Durable persistent state (v0.6).** `agentguard serve` is now stateful by default: the approval queue, rate-limit buckets, and cost accumulators survive a restart. New `pkg/store` (`Store` interface + `SQLiteStore`, pure-Go `modernc.org/sqlite`, WAL) and `pkg/persist` (write-behind syncer). On boot the syncer hydrates the in-memory maps from the store; a background ticker (hard ≥1 s floor) and graceful shutdown flush snapshots back. The store is a **cold-path** component — never read or written on the `/v1/check` request path, so the <3 ms p99 budget is preserved (measured p99 0.53 ms with persistence on). New `serve` flags: `--persist` (default `true`), `--store-dsn`, `--data-dir`, `--audit-backend=file|store`. `--persist=false` restores the legacy pure-in-memory behavior.
- **Multi-tenant policies (v0.6).** Tenants beyond `local` can be registered (store `policies` table + `policy.MultiTenantProvider`) and are evaluated against their **own** policy through the existing `/v1/t/<tenant>/...` routes, with isolated approvals, rate limits, cost accumulators, and audit. New `agentguard tenant put|list|rm` subcommand manages them. A tenant with no registered policy denies with `deny:tenant:not_found`; an infrastructure (store) failure denies with `deny:tenant:provider_error`. Non-local policies are parsed once and cached in memory, so per-tenant evaluation never hits the DB on the hot path.
- **Tenant-keyed runtime state + audit `tenant_id` (v0.6).** Every per-request store is partitioned by tenant: rate-limit bucket key `scope:tenant:agent`, session-cost accumulator `(tenant, session)`, and the approval queue's `Lookup`/`Resolve`/`List`/SSE scoped per tenant (a foreign tenant's id returns "not found" — no cross-tenant existence oracle). The audit schema gained an additive `tenant_id` field/column, and `/v1/t/<tenant>/audit` is now scoped to its tenant — **closing a cross-tenant audit-read leak**. Single-tenant (`local`) output stays byte-identical (the local tenant is stored as `""`), so the audit `schema_version` is unchanged.

### Fixed
- **Cross-transport policy-verdict skew** (gate/adapter consolidation) — the same tool call could produce different action-keyed rule matches depending on transport. CrewAI's adapter never sent the inferred filesystem `action` (LangChain's did); the MCP gateway didn't recognise `cat`/`find`/`glob` as read verbs (the LLM proxy did); the Python MCP adapter missed `create`→`write`. All transports now share one inference (`pkg/internal/gateclient.InferFilesystemAction`, `agentguard/adapters/_common.py`). Operators whose policies key on `action` may see new (correct) matches through CrewAI/MCP.
- **MCP gateway: unrecognised `/v1/check` decision strings** now deny with the stable `Rule="deny:gateway:invalid_response"` (parity with the LLM proxy's `deny:llm_api_proxy:invalid_response`) instead of passing the malformed verdict through bare. Add the new rule to outage/alerting dashboards.
- **`/v1/check` User-Agent version skew** — both proxies stamped a hard-coded `…/1.0` on the side-channel call while reporting the real build version elsewhere; they now report `BuildVersion`/`GatewayBuildVersion` consistently.
- **MCP gateway flag validation parity** — `--tenant-id` must be non-empty and `--guard-url` must be an http(s) URL, matching the LLM proxy.
- **Flaky concurrent-stream cap tests** — the three `TestServer_MaxConcurrentStreams_*` tests polled a real-time gauge against a wall-clock deadline and starved under full-suite parallel load. Replaced with a deterministic barrier: the test upstream signals once per admitted+forwarded stream, and the test drains N signals before asserting. No timing dependence.

- **Policy watcher transient-read race** (`pkg/policy/watcher.go`) — an atomic-replace policy edit (write-temp + rename) racing `reload` on Windows leaves the destination briefly locked after `MoveFileEx`, so the reload's open-for-read returns `ERROR_SHARING_VIOLATION`; that failed read was swallowed and, on the event-driven fsnotify path (no periodic tick), the change was lost until the next unrelated event. `reload` now retries transient `*fs.PathError` reads with a small bounded backoff (parse/validation errors surface immediately); the retry runs on the watcher's background goroutine, off the request path. Stabilizes the previously-flaky `TestATIntegration_ProviderReloadE2E` / `TestFilePolicyProvider_WatchCallbackPanicDoesNotKillWatcher` / `TestATFilePolicyProvider_RaceWatchGetMutate`.

### Changed
- **Internal consolidation (no wire-format change).** The `/v1/check` client, fail-mode translation, `Decision` type, and shared gate CLI flags now live once in `pkg/internal/gateclient` (both proxies re-export `Decision` via type alias — public APIs unchanged). Python adapters share `adapters/_common.py` for check-param extraction; the SDK split into `core.py`/`decorators.py` with the package root re-exporting everything (imports and mock-patch targets unchanged).
- **`pkg/metrics` is now a `Registry`** with package-level delegates to `Default`; exported raw counter vars became same-named accessor functions and the exported histograms became `Observe*Duration` functions (Go API change for direct importers; Prometheus exposition is byte-identical). `metrics.Reset()` added for test isolation.
- **Audit pipeline construction** extracted from `runServe` into `cmd/agentguard/audit_setup.go` with explicit shutdown ordering; the never-wired `audit.SQLiteLogger` prototype was removed (the store backend `--audit-backend=store` is the live SQLite path). File/store backend `QueryFilter` semantics are pinned by a parity test.
- **Repo hygiene:** `.gitattributes` forces LF for `*.go` (gofmt is meaningful on Windows checkouts); repo-wide gofmt pass.

- **`serve` is stateful by default.** A first run creates `agentguard.db` (+ `-wal`/`-shm` sidecars, now gitignored) in the working directory. This is additive — the wire contract (`schema_version: v1`, the `/v1/t/{tenant}/...` routes) is unchanged, and `--persist=false` reverts to the prior behavior.

- **`/v1/t/{tenant}/...` tenant-aware route family** — every operational endpoint mirrored under a tenant-aware path. v0.5 only recognises `local`; v0.6 swaps in a multi-tenant `PolicyProvider`.
- **`agentguard check` CLI subcommand** — one-shot policy check (or batch from JSONL stdin) against a local policy file without going through the HTTP server. Per-field flags, `--request '<json>'`, `--stdin`, `--batch`, `--output text|json`, structured exit codes (`0` allow, `1` deny, `2` approval, `3` error).
- **`--debug-pprof` / `--debug-pprof-port` serve flags** — expose Go pprof handlers on a separate localhost-only listener (default `127.0.0.1:6060`). Off by default; tunnel via `kubectl port-forward` or `ssh -L` for remote access.
- **`--audit-buffered`, `--audit-queue-size`, `--audit-workers`, `--audit-overflow-path` serve flags** — wire the `BufferedAsyncLogger` (Phase 2 A6) so the `/v1/check` hot path no longer waits on the audit mutex. On by default; `--audit-buffered=false` restores the synchronous v0.4.x path.
- **JSON-RPC error codes for the MCP Gateway**: `-32000` (`ErrCodePolicyDeny`), `-32001` (`ErrCodePolicyApproval`), `-32002` (`ErrCodeUpstreamUnavail`). Wire-protocol contract for MCP clients to branch on.
- **`--policy` flag on `agentguard-llm-proxy`** — loads the central policy YAML for `tool_scope_map` operator overrides.
- **`--policy` and `--policy-mode strict|fast` flags on `agentguard-mcp-gateway`** — `strict` (default) requires `--policy`; `fast` skips loading and uses bundled defaults.
- **LLM streaming buffer cap** — `--max-buffer-bytes` (default `1048576`, ceiling `MaxConfigurableBufferBytes = 64 MiB`) per tool-call accumulator.
- **Provider-aware synthetic refusal payloads** — `pkg/llmproxy/refusal.go` emits OpenAI-style assistant-text + `[DONE]` and Anthropic-style `content_block_*` shapes that match what each SDK expects.
- **New Prometheus metrics**: `agentguard_llmproxy_buffer_overflow_total`, `agentguard_llmproxy_active_streams` (process-local on the LLM proxy); central server gains the `transport` label on existing decision counters.

### Changed

- **Audit log rotation is wired by default.** Previously, the rotation primitives existed in `pkg/audit` but were not constructed by `runServe`; size-triggered rotation now runs out of the box. Defaults: `--audit-max-size-mb 100`, `--audit-max-backups 5`, `--audit-max-age-days 30`, `--audit-compress true`. Rotated files are gzipped and carry a `_meta.rotated_from` pointer so startup replay walks the rotation chain. Operators who relied on external rotation can disable the built-in rotator via `--audit-max-size-mb 0`.
- **`conditions.time_window` without `require_prior` is now a hard load error** (`errorTimeWindowOnlyConditions`). v0.4.x emitted only a WARNING; v0.5 promotes it to a load failure that aborts `serve` startup and hot-reload. Operators upgrading must remove time-window-only conditions from their policies first. `docs/MIGRATION.md` § v0.4.1 → v0.5 documents the upgrade path.
- **Python SDK drops Python 3.8 support.** `pyproject.toml` requires `>=3.9`; CI matrix runs 3.9 / 3.10 / 3.11 / 3.12. 3.8 reached upstream EOL in October 2024.

### Fixed

- (no v0.5-specific fixes beyond those rolled into the above; security findings tracked in the v0.5 audit reports.)

## [0.4.1] — 2026-04-22

*(Corrected in v1.1.1: 0.4.1 was never tagged or published — no Go module version or PyPI release exists. These changes first shipped in an installable release in 0.5.0.)*

> This release focuses on behavioral fixes and observability. Server behavior changes are opt-in or clearly surfaced; SDK and audit-log contracts remain backward-compatible with v0.4.0.
>
> **Operators upgrading from v0.4.0 should read `docs/MIGRATION.md`.** The audit log is migrated in place on first start; a byte-for-byte backup is preserved at `<audit-log>.v040-backup` so downgrade stays possible through v0.4.2.

### Added

- `docs/DEPRECATIONS.md` — single-source-of-truth table for features scheduled for removal, with `deprecated-in`, `removal-target`, and `migration-path` columns. New entries land in the same commit as the code that introduces them.
- `docs/FILE_FORMATS.md` — documents the `schema_version` convention for every on-disk artifact AgentGuard writes, plus non-version identifiers (User-Agent, MCP protocol) that deliberately do not track the release version.
- `pkg/deprecation` helper — `deprecation.Warn(feature, msg)` logs once per process per feature key and increments a counter exposed at `agentguard_deprecations_used_total{feature="..."}`. Scrape this before a planned removal release to see whether anyone is still using a feature.
- `agentguard migrate` subcommand — runs on-disk schema migrations with `--dry-run`, `--list`, `--id=<name>` (operator override to re-run a specific migration), and `--reset-checkpoint` (force next start to do a full replay).
- `pkg/migrate` framework — `Migration` interface and registry used by `RunStartup()` (auto at boot) and `RunCLI()` (via `agentguard migrate`). Each concrete migration lives under `pkg/migrate/vNNN_to_vMMM/`.
- `proxy.tls.terminated_upstream` config flag — when true, session cookies are issued with `Secure` regardless of `r.TLS`. Off by default; turn it on when AgentGuard is behind a TLS-terminating reverse proxy that does not pass `X-Forwarded-Proto`.
- `notify.redaction.extra_patterns` config — operator-supplied regexes appended to the built-in redactor defaults. Compiled and validated at startup.
- Python SDK `fail_mode` parameter (default `"deny"`) — matches the existing knob on the TypeScript SDK. v0.4.1 does not change defaults; v0.5.0 will align both SDKs explicitly on `"deny"` in release notes.
- Observability (Phase 3):
  - `agentguard_notify_events_dropped_total{notifier,reason}` — was an unexposed `notify.DroppedEvents` atomic.
  - `agentguard_notify_queue_depth{notifier}`, `agentguard_notify_dispatch_duration_seconds{notifier}`.
  - `agentguard_sse_events_dropped_total{client_id}`, `agentguard_sse_subscribers`.
  - `agentguard_ratelimit_buckets`, `agentguard_ratelimit_bucket_evictions_total{scope}`.
  - `agentguard_approvals_pending`, `agentguard_approvals_evicted_total{reason}`.
  - `agentguard_request_rejected_total{reason="body_too_large"}`.
  - `agentguard_audit_replay_duration_seconds`, `agentguard_audit_replay_entries_total`, `agentguard_audit_rotations_total`, `agentguard_audit_migration_status{from,to,status}`.
- Config keys (Phase 4) — new keys with safe defaults, all documented in `docs/CONFIG.md`:
  - `proxy.session.ttl` (default `1h`)
  - `proxy.request.max_body_bytes` (default `1048576`)
  - `proxy.audit.default_limit` (default `100`) and `proxy.audit.max_limit` (default `1000`)
  - `notify.dispatch_timeout` (global + per-notifier, default `10s`)

### Changed

- Audit log format bumped to `schema_version: 2`. A meta-record `{"_meta": {"schema_version": 2, ...}}` is now the first line of every audit file. Readers at v0.4.1+ accept v1 (headerless, written by v0.4.0) transparently — the `v040_to_v041` migration rewrites the file in place on first start and preserves a `.v040-backup` copy for downgrade. See `docs/MIGRATION.md`.
- Audit log rotation primitives landed in `pkg/audit` (size-triggered rotator, gzip + `_meta.rotated_from` chain). They are *not yet wired into the default `runServe` path* — the v0.5 release wires them by default. Operators on v0.4.1 should continue to rotate `audit.jsonl` externally.
- Audit replay is now checkpointed at `<audit-log-path>.replay-checkpoint`, so a restart no longer re-scans the whole history to seed counters. The checkpoint is written atomically (`write + rename`); a missing, corrupt, or stale (file-truncated) checkpoint silently triggers a full rescan on next boot. Run `agentguard migrate --reset-checkpoint` (or just delete the file) to force that explicitly.
- `/v1/audit` now honors `?limit` (clamped to `[1, 1000]`, default `100`) and `?offset`. Previously, `?limit` was silently ignored and hard-coded to `100`.
- `ApprovalQueue` eviction is LRU instead of "drop every resolved entry at once". When the queue is at capacity, the oldest resolved entry is evicted first; if none are resolved, new approvals are rejected with `503 Service Unavailable` and a `Retry-After` header rather than silently dropped.
- Session store: when the in-memory session cap (`MaxSessions = 1024`) is reached, new logins receive `503` with a clear message instead of silently evicting the oldest active session. Heavy dashboard users who previously hit the cap will notice a visible failure where there used to be a silent one.
- Policy watcher uses fsnotify to detect atomic-replace rewrites immediately, with a 2 s poll fallback when fsnotify is unavailable. No user-visible contract change.
- `sessionCosts` map has an opt-in TTL sweep goroutine (`--session-cost-ttl`, `--session-cost-sweep-interval`) so long-running servers do not accumulate per-session cost entries indefinitely. Defaults to disabled (`0`), preserving v0.4.0 behavior; sweep interval defaults to `max(ttl/4, 1m)` when only the TTL is set.
- Histogram buckets for `agentguard_*_duration_ms` extend past 1 s (new 2500 ms, 5000 ms, 10 000 ms buckets) to capture tail behavior under load. Not configurable: altering bucket boundaries later invalidates historical data.
- Webhook notifier honors the new `notify.dispatch_timeout`; the hard-coded 10 s falls away.

### Fixed

- Requests that exceed `MaxRequestBodySize = 1 MB` are now logged at WARN with `agent_id`, size, and limit, and increment `agentguard_request_rejected_total{reason="body_too_large"}`. Previously silent.
- Notification dispatcher queue-full drops are exposed via Prometheus (`agentguard_notify_events_dropped_total{notifier,reason}`); the `notify.DroppedEvents` atomic is no longer the only place you could see them.

### Deprecated

- `policy.time_window_without_require_prior` — rules that declare `conditions.time_window` without `require_prior` are a no-op today (v0.4.0 pass-through behavior). As of v0.4.1 they emit a deprecation warning on load and increment `agentguard_deprecations_used_total{feature="policy.time_window_without_require_prior"}`. **v0.5.0 will make this a load error.** Migration: pair `time_window` with `require_prior`, or remove `time_window` from the rule.
- `audit.migration.v040_to_v041` — the in-binary v0.4.0 → v0.4.1 migration is scheduled for removal in v0.4.3. Users upgrading past v0.4.2 must either have run through v0.4.1/v0.4.2 on the way, or use the standalone `agentguard-migrate` binary to convert headerless v1 audit files first.
- `audit.backup.v040` — `.v040-backup` rollback files are written by the migration and retained through v0.4.2 so operators can downgrade without tooling. v0.4.3 removes both the migration and the backup mechanism.

### Security

- Filesystem deny rules could be bypassed via path traversal (`../` segments). Request paths are now normalized with `filepath.Clean` before rule matching, and paths containing `..` after normalization are rejected outright. Policy files with `..` in filesystem rule patterns are also rejected at load time. _(Carried over from the unreleased entry above.)_

### Internal

- `pkg/migrate/v040_to_v041/removal_deadline_test.go` — fails once the server version reaches `0.4.3` while the migration package still exists. Forces the conversation on schedule; the deadline cannot slip silently.
- MCP adapter logs a WARN when a client requests a newer protocol than the pinned `2024-11-05`, still pinning our side. Actual version negotiation is a v0.5.0 design item.
